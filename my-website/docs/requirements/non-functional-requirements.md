# Нефункциональные требования

## Security — безопасность

| ID | Требование | Приоритет | Обоснование |
|---|---|---|---|
| NFR-SEC-001 | Все соединения клиентских интерфейсов с сервером должны выполняться только по HTTPS с использованием TLS 1.3 | Must | Передаются персональные данные клиента: ФИО и телефон. Без шифрования есть риск перехвата и утечки данных |
| NFR-SEC-002 | Система должна разграничивать права доступа по ролям: клиент, инструктор, администратор | Must | Клиент должен видеть только свои записи, инструктор — только свои смены и записи, администратор — данные смены и справочники |

## Performance — производительность

| ID | Требование | Приоритет | Обоснование |
|---|---|---|---|
| NFR-PERF-001 | Операции поиска слотов, поиска инструкторов и создания записи должны выполняться с временем ответа API не более 800 мс по p95 при нагрузке до 50 RPS | Should | Долгая запись снижает конверсию и увеличивает количество незавершенных попыток записи |

## Reliability — надежность и доступность

| ID | Требование | Приоритет | Обоснование |
|---|---|---|---|
| NFR-REL-001 | Доступность веб-сервиса и АРМ администратора должна быть не ниже 99.5% в месяц в сезон | Should | Сбой в пиковый день приводит к потере выручки и усложняет работу администраторов |

## Capacity — емкость

| ID | Требование | Приоритет | Обоснование |
|---|---|---|---|
| NFR-CAP-001 | Система должна поддерживать хранение минимум 10 000 клиентов за сезон и 100 000 записей за сезон без деградации ключевых операций | Should | Система должна выдерживать сезонную нагрузку без ухудшения поиска слотов и создания записей |

## Observability — наблюдаемость

| ID | Требование | Приоритет | Обоснование |
|---|---|---|---|
| NFR-OBS-001 | Система должна логировать события создания, подтверждения, отмены и переноса записи, изменения смен и блокировок, а также ошибки отправки уведомлений | Should | Логи нужны для разбора инцидентов, восстановления истории действий и подготовки отчетов |
| NFR-OBS-002 | Логи событий должны храниться не менее 90 дней | Should | Такой срок позволяет разбирать спорные ситуации и технические инциденты после их возникновения |

## Usability — удобство использования

| ID | Требование | Приоритет | Обоснование |
|---|---|---|---|
| NFR-UX-001 | Пользователь должен иметь возможность создать запись не более чем за 6 шагов от выбора категории до подтверждения | Should | Чем короче путь записи, тем выше вероятность, что клиент завершит сценарий |
| NFR-UX-002 | Форма ввода данных клиента должна содержать минимальный набор обязательных полей: ФИО, телефон, уровень катания и согласие с пользовательским соглашением | Should | Минимизация обязательных полей снижает количество незавершенных записей |

## Maintainability — поддерживаемость

| ID | Требование | Приоритет | Обоснование |
|---|---|---|---|
| NFR-MNT-001 | API системы должно быть документировано в формате OpenAPI 3.0 | Could | Документация API упрощает разработку, тестирование и дальнейшее сопровождение системы |
| NFR-MNT-002 | Конфигурации окружений должны быть описаны так, чтобы новый релиз можно было развернуть по инструкции | Could | MVP быстро меняется, поэтому без описания окружений сопровождение будет сложнее |

## Compatibility — совместимость

| ID | Требование | Приоритет | Обоснование |
|---|---|---|---|
| NFR-COMP-001 | Веб-интерфейс клиента должен корректно работать в последних двух версиях Chrome, Safari и Firefox | Should | Клиенты используют разные браузеры, поэтому базовая совместимость критична для доступности сервиса |
| NFR-COMP-002 | Веб-интерфейс клиента должен быть адаптивным для экранов шириной от 360px | Should | Клиенты часто записываются с телефона, поэтому интерфейс должен быть удобен на мобильных устройствах |

## Scalability — масштабируемость

| ID | Требование | Приоритет | Обоснование |
|---|---|---|---|
| NFR-SCAL-001 | Архитектура должна позволять увеличить пропускную способность минимум в 3 раза без изменения бизнес-логики приложения | Could | В праздники и высокий сезон возможны пики нагрузки, поэтому система должна иметь запас для роста |

## Legal / Compliance — нормативно-правовые требования

| ID | Требование | Приоритет | Обоснование |
|---|---|---|---|
| NFR-LGL-001 | Создание записи должно быть возможно только после фиксации согласия клиента с пользовательским соглашением и обработкой персональных данных | Must | Система обрабатывает ФИО и телефон клиента, поэтому требуется юридически корректное согласие |
| NFR-LGL-002 | Система должна хранить факт согласия клиента: дату, время и версию соглашения | Must | Это снижает юридические риски и позволяет подтвердить факт согласия при спорных ситуациях |
